# PAN-1326 manual dashboard stop verification

Purpose: verify the fix from commit `bd7d00787`, where dashboard stop/kill now resolves the workspace stack from the issue instead of trusting specialist agent state.

Original test-plan item: "Manual: kill a ship specialist via dashboard, confirm `docker ps` no longer shows that issue's stack".

## Prerequisites

1. Use a workspace issue with a running Docker stack.
2. If needed, start one from the project root:
   ```bash
   pan start PAN-XXXX
   ```
3. Confirm the stack is visible before stopping anything:
   ```bash
   docker ps --format '{{.Names}}' | grep 'panopticon-feature-pan-xxxx'
   ```
   Expected: issue-scoped containers such as frontend/dev/server containers are listed.
4. Ensure a specialist exists for that issue, preferably `ship` or `test`. If there is no specialist, start the normal pipeline path that creates one rather than editing state by hand.

## Steps

1. Open the dashboard.
2. Find the issue card for the workspace from the prerequisites.
3. Open the agent/specialist controls for a `ship` or `test` specialist on that issue.
4. Click the stop button for that specialist.
5. Wait for the dashboard to show the specialist as stopped.
6. Check the agent lifecycle/output logs for:
   ```text
   [agents] ✓ Stopped Docker stack for <agentId>
   ```
7. Re-run the Docker check:
   ```bash
   docker ps --format '{{.Names}}' | grep 'panopticon-feature-pan-xxxx'
   ```

## Expected evidence

Before the stop: `docker ps` lists the issue's workspace containers.

After the stop: `docker ps` no longer lists that issue's stack, and the dashboard/server log includes `[agents] ✓ Stopped Docker stack for <agentId>`.

## Regression signal

If the specialist is stopped but `docker ps` still shows the issue's stack, PAN-1326 has regressed. The original symptom was that specialist state had no usable `workspace`, so dashboard stop skipped or targeted the wrong Docker stack.
