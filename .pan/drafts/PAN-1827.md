# PAN-1827 — Conversation view blank for pi-harness sessions

**Issue:** https://github.com/eltmon/panopticon-cli/issues/1827
**Planning mode:** `pan plan --auto` (non-interactive; choices recorded as autoDecisions)

## Problem

The flywheel orchestrator (kimi-k2.6 on the **pi** harness) and every other
pi-harness pipeline agent (work, strike) render an empty conversation view in
the Command Deck. The shared transcript resolver
`src/dashboard/server/routes/jsonl-resolver.ts` dispatches on the harness
recorded in `state.json` with branches only for **claude-code** (project JSONLs)
and **codex** (PAN-1805 rollout JSONLs). There is no **pi** branch, so for a pi
agent the resolver falls through to the claude-code lookup, finds no
`~/.claude/projects/.../<id>.jsonl`, and returns null — `hasJsonl` becomes
`false` and the panel shows "No conversation data available for this session."

Same bug class as PAN-1805 (codex), third harness.

## Investigation (verified against the codebase 2026-06-13)

Two resolvers carry a codex branch but no pi branch:

1. **Path A — `resolveJsonlPath`** (`jsonl-resolver.ts:204-223`). Dispatches
   `resolveAgentHarness === 'codex'` → `resolveCodexRolloutPath` (line 211),
   else `resolveClaudeSessionId` + claude-projects lookup. Used by
   `command-deck.ts` (incl. the flywheel orchestrator section, line 517),
   `projects.ts`, and `reviewer-tree.ts` to compute the `hasJsonl` flag. With no
   pi branch, pi agents get `hasJsonl: false` and the SessionPanel can't even
   build `synthesizedConversation` (`SessionPanel.tsx:237`).

2. **Path B — `/api/conversations/:name/messages` fallback**
   (`conversations.ts:3013-3066`). For a pipeline agent NOT in the conversations
   DB it checks `resolveAgentHarness(name) === 'codex'` →
   `resolveCodexRolloutPath` (lines 3017-3024), else scans `~/.claude/projects`.
   No pi branch. Additionally its prefix guard
   `/^(specialist-|agent-|planning-)/` (line 3013) **omits `strike-`** — strike
   agents are named `strike-<issue-id>` (canonical `AGENT_PREFIXES` in
   `agents.ts:582` = `['agent-','planning-','conv-','strike-','inspect-']`), so
   strike agents never reach harness resolution at all.

The pi conversation parser already exists and is already wired into the parse
dispatch: `getCachedMessages` (`conversations.ts:3078`) → `isPiSessionFile` →
`parsePiConversationMessages` (`conversations.ts:545`,
`pi-conversation-parser.ts:27`). `isPiSessionFile` matches
`/\.panopticon/agents/<id>/sessions/` — exactly the path a pi resolver
produces. So **no new parser is required**; the resolved path simply needs to
reach the existing dispatch.

Pi session files: `PiRuntimeSync.getSessionPath` (`pi.ts:125`) resolves the
freshest `.jsonl` under `<agentDir>/sessions/` (nested
`sessions/<encoded-cwd>/<timestamp>_<id>.jsonl`, tolerant of any depth). The
per-agent `sessions/` dir holds only this agent's sessions, so freshest-by-mtime
is the live transcript — the same reasoning codex uses for per-agent CODEX_HOME.
That sync method must NOT be called from the resolver (it uses `readdirSync`);
the resolver runs in the dashboard event loop and must be async (`fs/promises`).

The flywheel orchestrator (`flywheel-orchestrator`) is a **registered
conversation** (`FlywheelConversationPane` finds it by name;
`flywheel.ts:61`), so `getConversationByName` → `resolveSessionFile` pi branch
(`conversations.ts:754`) already resolves it for the flywheel pane. Its blank
state is the **agent-tree** view (Path A).

## Proposal

Mirror the codex pattern in the two codex-aware resolvers:

1. Add `resolvePiSessionPath(agentId, opts)` to `jsonl-resolver.ts` (async,
   mirrors `resolveCodexRolloutPath`): walk `<agentsDir>/<agentId>/sessions/`
   recursively for `.jsonl` files and return the freshest by mtime, or null.
   Add a `'pi'` branch to `resolveJsonlPath` dispatch **before** the claude
   fallback.
2. Add a `'pi'` branch to the `/messages` fallback (mirror the codex branch),
   and extend its prefix guard to include `strike-` and `inspect-`.
3. Regression tests in `jsonl-resolver.test.ts` mirroring the codex cases.

## Requirements

### Functional
- **FR-1** — `resolveJsonlPath` returns the freshest pi session JSONL for an
  agent whose `state.json` harness is `pi`.
- **FR-2** — The pi harness branch is dispatched **before** `resolveClaudeSessionId`,
  so pi's own `session.id` file (a pi session id, `pi.ts:97`) cannot be
  misresolved to a non-existent `~/.claude/projects/.../<id>.jsonl`.
- **FR-3** — `resolvePiSessionPath` returns null when the agent has no
  `sessions/` directory or it contains no `.jsonl`.
- **FR-4** — The `/api/conversations/:name/messages` fallback resolves the pi
  transcript (via `resolvePiSessionPath`) for pipeline agents not in the
  conversations DB, so their `messages` array is populated.
- **FR-5** — The `/messages` fallback prefix guard matches `strike-` and
  `inspect-` session names, so strike agents reach harness resolution.

### Non-Functional
- **NFR-1** — The resolver uses async `fs/promises` only (no `*Sync`, no
  `execSync`) — it runs inside the dashboard server event loop.
- **NFR-2** — claude-code and codex resolution are unchanged in both resolvers
  (no regression to existing harnesses).

## Non-Goals

- Do NOT modify `/api/agents/:id/conversation` (`buildConversationResponse` →
  `getAgentJsonlPath` in `agent-enrichment.ts`). It is claude-only and lacks
  even a codex branch — a separate, pre-existing gap (affects codex too).
  Recommend a follow-up issue.
- Do NOT write a new pi conversation parser — `parsePiConversationMessages` /
  `isPiSessionFile` already exist and are reused.
- Do NOT change pi spawn / runtime / session-file writing.
- Do NOT modify the registered-conversation path (`resolveSessionFile`,
  `conversations.ts:754`) — it is already pi-aware.
