# PAN-1832 — Role Models: multiple models per role with weighted distribution

**Issue:** https://github.com/eltmon/panopticon-cli/issues/1832
**Status:** planning (discovery)

## Problem

Each pipeline role (`plan`/`work`/`review`/`strike`/`flywheel`, plus sub-roles like
`review.security`) binds to a **single** model in Settings → Roles (or a workhorse tier).
When a fleet runs many agents of one role they all hit the same provider and exhaust its
rate limits (repeated gpt-5.5 rate-limit modals stalling reviewers — see #1830). The team
currently hand-splits the fleet ~30/70 gpt-5.5/kimi to spread load. Make that split
first-class.

## Desired behavior (from issue)

- A role's `model` field accepts EITHER a single ref (today's behavior, unchanged) OR a
  list of `{ model: <ref>, weight: <int> }`.
- Each spawn resolves its model by sampling the distribution (e.g. work = 70% kimi / 30%
  gpt-5.5). Harness follows from the chosen model via `resolveHarness()` (PAN-1787), so one
  role can mix harnesses across agents.
- Validation: every model in the list passes `hasModelCapabilitySync`; weights are positive
  ints.
- Config schema (`config-yaml.ts`) + settings API accept the list form; scalar back-compat
  preserved.
- Picker UI shows the distribution, lets you add/remove models + set weights.
- Observability: each agent's chosen model is already recorded in `state.json`.

## Discovery findings (verified 2026-06-13)

### Core resolution seam
- `resolveModel(role, subRole?, config)` — `src/lib/config-yaml.ts:1576` — the central,
  **deterministic** resolver. Reads `roles[role].model` (or `.sub[subRole].model`), derefs
  `workhorse:` refs via `derefWorkhorse()` (`config-yaml.ts:1555`), returns one `ModelId`.
- `determineModel({ model?, role? })` — `src/lib/agents.ts:2619` — spawn-time wrapper for
  **work** agents. Calls `resolveModel` when no explicit override; applies the
  WORK_AGENT_BROKEN_MODELS safety net.

### Spawn sites that resolve a role model (each has a stable agent id usable as seed)
1. **work** — `spawnAgent` (`agents.ts:3444`); agent id `agent-<issue>` computed at :3449
   BEFORE `determineModel` at :3469; model persisted to `state.model` at :3506. Also routed
   via `spawnRun` (`agents.ts:3131`, `determineModel` at :3133).
2. **review convoy** — `review-agent.ts:236` `resolveModel('review', subRole, cfg)`; stable
   id `reviewerAgentId(issueId, subRole)`.
3. **work.inspect / inspect-deep** — `inspect-agent.ts:176` `resolveModel('work', subRole, …)`.
4. **plan** — `spawn-planning-session.ts:556` `resolveModel('plan', undefined, …)`.
5. **test** — resolves via role primitive (`specialist-context.ts:128`).

### Static (deterministic) callers of resolveModel — MUST stay deterministic
- `router-config.ts:152-158` builds the (deprecated CCR) static `role:*` map.
- `settings-api.ts:524` effort-validation derefs the role model to one id.
- These must NOT randomly sample. Plan: `resolveModel()` keeps returning a single
  representative (the first / highest-weight entry) for list configs; sampling lives in a
  NEW spawn-only resolver seeded by agent id.

### Config & settings round-trip
- `RoleConfig.model: ModelRef` (string) — `config-yaml.ts:347`. `DEFAULT_ROLES` etc. at :387.
- `validateModelRef()` — `settings-api.ts:403` — validates a single string ref.
  `validateWorkhorsesAndRoles()` (:484) walks roles/sub-roles.
- GET serializer `seededRoles()` (`settings-api.ts:301`) spreads the role verbatim — a list
  `model` round-trips transparently.
- PUT `/api/settings` (`routes/settings.ts:877`) → `validateSettingsApi` → `saveSettingsApi`
  writes yaml. List form persists if the type allows it and validation passes.
- Frontend types are LOCAL to `RolesPanel.tsx` (no shared `@panctl/contracts` RoleConfig) —
  `RoleConfig.model?: ModelRef` at :18, single `<select>` `ModelPicker` at :321,
  `saveRoleConfig` at :271.

### Constraints to honor
- **No `Math.random()`** in resolution paths — must use a seeded/deterministic pick
  (issue's own open question). Seed = the agent id (stable per agent).
- **JSONL resume hazard** (concerns.md) — must NOT re-sample a different model on
  resume/restart of an existing agent (corrupts the session). Seeding by the stable agent id
  makes sampling idempotent; resume already reads `state.model`, never re-resolves.
- `canUseHarnessSync` ToS gate + `resolveHarness` precedence unchanged — harness still
  derives from the chosen model post-sample.

## Planning Q&A

### Q1 — Sampling strategy (2026-06-13)
Options: (a) Hash of agent id [Recommended]; (b) Stateful round-robin counter.
**Answer: (a) Hash of agent id.** Sampler = `hash(agentId) mod totalWeight`, walk cumulative
weights. Stateless, deterministic per agent, idempotent on resume (no model switch → safe for
the JSONL-resume hazard). Seed is the stable agent id.

### Q2 — Weight validation (2026-06-13)
Options: (a) Normalize relative weights [Recommended]; (b) Strict sum-to-100.
**Answer: (a) Normalize.** Accept any positive ints; sample proportional to their sum. UI shows
effective % live. Save is never blocked on an off-by-one sum. (Still reject: empty list,
non-positive / non-integer weights, zero total.)

### Q3 — Realized-split dashboard view (2026-06-13)
Options: (a) Follow-up issue [Recommended]; (b) Include in this issue.
**Answer: (b) Include in this issue.** Build a dashboard view that aggregates live agents'
`state.model` into realized-vs-configured per role (e.g. "work: 18 kimi / 7 gpt-5.5, target
70/30").

### Defaults accepted (operator did not object)
- **Uniform coverage**: the list form is supported on every role AND sub-role
  (`review.security` etc. are exactly the rate-limit pain point per #1830).
- **Flywheel per-model slot caps**: OUT of scope (the issue itself defers it → NonGoals).

## Requirements

### Functional
- **FR-1** — `roles.<role>.model` and `roles.<role>.sub.<subRole>.model` accept EITHER a scalar
  model ref (today) OR a list `[{ model: <ref>, weight: <int> }, …]`.
- **FR-2** — Scalar `model` behavior is byte-for-byte unchanged (back-compat).
- **FR-3** — Each pipeline spawn samples its model deterministically via
  `hash(agentId) mod Σweights`, walking cumulative normalized weights. Same agent id ⇒ same
  model (idempotent on restart/resume — no model switch). No `Math.random()`.
- **FR-4** — Sampling applies to every pipeline spawn role: work, test, ship, strike (via
  `determineModel`), review + review sub-roles, work.inspect/inspect-deep, plan, and flywheel
  (flywheel is a singleton ⇒ a list resolves to one deterministic pick, documented).
- **FR-5** — Settings-API PUT validates the list form: non-empty; each entry `{model:string,
  weight:int>0}`; each model passes `validateModelRef` (workhorse refs allowed); `parent` is
  rejected inside a list; total weight > 0. Weights are NORMALIZED (no sum-to-100 requirement).
- **FR-6** — config-load (`config-yaml.ts`) validates the list form and fails fast on bad
  hand-edited yaml (each ref derefs, weights positive ints, non-empty, no `parent` in list).
- **FR-7** — A role's `effort` must be supported by EVERY model in its distribution, else the
  save is rejected (per-model effort is out of scope).
- **FR-8** — Settings → Roles picker lets the user edit a distribution: toggle single↔split,
  add/remove model rows, set integer weights, and see the live effective % per row.
- **FR-9** — The dashboard (Roles settings) shows the realized split per role: live agent counts
  grouped by `state.model` vs the configured target (client-side aggregation of `/api/agents`,
  which already returns per-agent `role`+`model`).
- **FR-10** — Harness still derives from the CHOSEN (sampled) model via `resolveHarness()`
  (PAN-1787) — verify, no logic change.

### Non-functional
- **NFR-1** — No `Math.random()` in any resolution path; deterministic FNV-1a/djb2 string hash.
- **NFR-2** — `resolveModel()` stays deterministic for static callers (router-config, effort
  deref, specialist status map, planning-continuation launcher) — they get the primary
  (first-entry) representative for a list config.
- **NFR-3** — No new event-loop-blocking server calls; realized-split reuses the existing
  cached `/api/agents` response.
- **NFR-4** — `npm run typecheck`, `npm run lint`, `npm test` green; new unit tests prove
  sampler determinism + approximate ratio + scalar back-compat.

## Design

- **Types (`config-yaml.ts`):** `RoleModelWeight {model: ModelRef; weight: number}`,
  `RoleModelDistribution = RoleModelWeight[]`, `RoleModelConfig = ModelRef |
  RoleModelDistribution`. `RoleConfig.model` and `RoleSubConfig.model` become `RoleModelConfig`.
- **`primaryModelRef(m)`** → scalar, or list[0].model. **`isModelDistribution(m)`** → Array.isArray.
- **`resolveModel()`** uses `primaryModelRef` then existing deref — stays deterministic.
- **Sampler:** `hashStringToUint32(seed)` (FNV-1a, pure) + `sampleModelRef(dist, seed)`
  (Σweights normalize, cumulative-walk). **`resolveModelForSpawn(role, subRole, seed, config)`**
  mirrors `resolveModel`'s parent/sub/default precedence but samples when the chosen
  ref-config is a list; sub-role `parent` inherits the parent role's (possibly-list) config
  and samples THAT.
- **Seed = the stable agent id** at each spawn site (work: `agent-<issue>`; review:
  `reviewerAgentId(issue, subRole)`; etc.) — embeds issueId so different issues realize the
  split, while a single agent is idempotent across resume.
- **Realized-split:** client-side aggregation in `RolesPanel` from `/api/agents` (already
  returns `role`+`model`); no new endpoint.
