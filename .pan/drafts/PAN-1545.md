# PRD: New Terminal Button — spawn ad-hoc bash sessions from the dashboard

**Issue:** [PAN-1545](https://github.com/eltmon/panopticon-cli/issues/1545)

*Author: Edward Becker · Drafted: 2026-05-27*

---

## Vision

A user clicks one of four buttons in the dashboard and lands at a fresh `bash` prompt inside the dashboard's terminal renderer. No agent, no conversation, no issue context required. Mirrors t3code's `terminal.open` UX so cherry-picks from upstream stay easy.

## Motivation

The dashboard can already *render* any tmux session on the `panopticon` socket via `/terminal/<sessionName>` — but the only way to create a session today is `pan start` (work agent), `pan plan` (planning agent), or starting a conversation. There's no path to "I just want a bash prompt." That gap is what this feature fills.

## Acceptance Criteria

1. `POST /api/terminals` creates a fresh tmux session and returns its name.
   - Body: `{ cwd?: string }`
   - Response: `{ sessionName: string, cwd: string }`
   - Session name auto-generated as `term-<unix-timestamp>-<short-rand>` (avoids collisions with `agent-*`, `conv-*`, `planning-*` patterns)

2. Four entry points trigger the create+navigate flow, each with the most relevant default cwd:
   - **Sidebar nav** — global "+ Terminal" item, no specific cwd (server defaults to `$HOME`)
   - **ConversationPanel header** — button, passes `conversation.workspacePath` as cwd
   - **IssueDrawer header** — button, passes `agent.workspace || issue.workspacePath` as cwd
   - **CommandPalette (Cmd-K)** — `PaletteAction` under Orchestration group, no specific cwd

3. Each entry point produces an identical end state: a browser tab on `/terminal/<sessionName>` with a working bash prompt at the chosen cwd.

4. Existing terminal / agent / conversation behavior is untouched.

## Non-Goals

- **Lifecycle management** — no close button, no list-and-kill UI, no auto-cleanup. Orphaned `term-*` sessions accumulate in tmux until manually killed. This is a follow-up issue.
- **Renaming** — no UI to rename ad-hoc sessions to stable names.
- **Multi-pane / tabs** — one terminal per page.
- **Wiring through the agent state machine** — these are NOT agents. They have no `state.json`, no `issueId`, no review/test/ship pipeline. They're plain tmux sessions.
- **Coupling to PAN-1536's RPC transport** — works with either raw `/ws/terminal` or `?terminal=rpc`.
- **Auth / multi-user concerns** — Panopticon is single-user. Anyone with dashboard access can spawn terminals.

## Architecture

```
┌──────────────────────────────────────────────────────────────────┐
│  4 entry points (frontend)                                       │
│  ─ Sidebar nav item                                              │
│  ─ ConversationPanel header button                               │
│  ─ IssueDrawer header button                                     │
│  ─ CommandPalette PaletteAction                                  │
│                                                                  │
│  ALL call: openNewTerminal(cwd?) ────────────────────────┐       │
└──────────────────────────────────────────────────────────────────┘
                                                          │
                            POST /api/terminals { cwd }    │
                                                          ▼
┌──────────────────────────────────────────────────────────────────┐
│  Server route: terminals.ts                                      │
│  ─ Generates name: term-<ts>-<rand>                              │
│  ─ Resolves cwd (body cwd or $HOME)                              │
│  ─ Spawns: tmux -L panopticon new-session -d -s <name> -c <cwd> bash │
│  ─ Returns: { sessionName, cwd }                                 │
└──────────────────────────────────────────────────────────────────┘
                                                          │
                            { sessionName, cwd }           │
                                                          ▼
┌──────────────────────────────────────────────────────────────────┐
│  Frontend helper: openNewTerminal                                │
│  ─ Navigates to /terminal/<sessionName>                          │
│  ─ (uses existing StandaloneTerminalRoute — no route changes)    │
└──────────────────────────────────────────────────────────────────┘
```

## Key Decisions

### Decision 1 — One shared helper, four thin wrappers

All four entry points call the same `openNewTerminal(cwd?: string): Promise<void>` function. Each entry point is ~5 lines: button + onClick handler. The actual logic (POST, navigate) lives in one place. Future changes (e.g. opening in a new tab vs current tab, error toast on failure) propagate to all four for free.

### Decision 2 — Session naming differentiates ad-hoc terminals

Naming pattern: `term-<unix-timestamp>-<4-char-rand>`. Example: `term-1716830493-a8f2`. This is distinct from:
- `agent-*` (work / plan / review / test / ship agents)
- `conv-*` (Panopticon-managed conversations)
- `planning-*` (legacy planning sessions, if any remain)
- Bare names users might pick manually

Distinct naming lets future cleanup logic identify ad-hoc sessions by prefix.

### Decision 3 — No state file, no agent record

Ad-hoc terminals do NOT create entries under `~/.panopticon/agents/`. They have no `state.json`, no role, no harness, no review pipeline. They are plain tmux sessions, period. The dashboard's resource-discovery service may surface them under "Other terminals" in a future iteration, but for v0 they are invisible to the dashboard's normal navigation — accessible only via the URL bar or by clicking the spawn button again (which always creates a NEW one).

### Decision 4 — cwd resolution policy

The server resolves cwd in this order:
1. If `body.cwd` is provided AND the path exists, use it.
2. If `body.cwd` is provided but doesn't exist, fall back silently to `$HOME` (don't error; better UX than refusing).
3. If no `body.cwd`, use `$HOME`.

No path validation against an allowlist — single-user assumption. The user clicking the button can already do anything bash can do.

### Decision 5 — Navigation: same tab vs new tab

For v0, **same tab**. The user explicitly chose to open a terminal; replacing the current view is fine. If they wanted to keep the current view, they could Cmd-click. A future setting could change this default, but it's not in scope.

## Out of Scope

- Cleanup of orphaned `term-*` sessions
- Listing ad-hoc terminals in the dashboard nav
- Renaming or re-attaching to a previously created ad-hoc terminal
- Custom shells (zsh, fish) — bash only
- Custom env vars / startup commands beyond what `tmux new-session` provides
- Resizing the initial pane dimensions (uses xterm.js defaults)

## Risks

| Risk | Mitigation |
| --- | --- |
| Orphaned sessions accumulate over time | Documented as known limitation; cleanup is a follow-up issue. User can `tmux -L panopticon kill-session -t term-*` to bulk-delete. |
| Conflicting session name (timestamp collision) | The 4-char random suffix gives 65k entropy; collision in the same second is effectively impossible. |
| User opens many terminals and each holds a node-pty + tmux client | Each terminal panel is ~5MB resident. 20 open terminals = 100MB. Not a hard cap; user can close tabs. |
| Spawning bash with the wrong env (e.g. inheriting Panopticon-internal vars) | Use `buildChildEnvWithoutTmuxSync()` helper (already used by ws-terminal.ts and terminal-service.ts). |

## Verification

For each entry point:
1. Click the button.
2. Browser navigates to `/terminal/term-...`.
3. Terminal panel shows a bash prompt.
4. `pwd` matches the expected cwd (sidebar/palette → `$HOME`; conversation → workspace path; drawer → workspace path).
5. Typing commands works; output renders.
6. Closing the tab does NOT kill the session (visible in `tmux -L panopticon list-sessions`).
