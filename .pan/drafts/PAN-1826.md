# PAN-1826 — Flagless `pan start` bypasses provider-default harness resolution

**Issue:** https://github.com/eltmon/panopticon-cli/issues/1826
**Date:** 2026-06-13 (auto planning session)
**Parent work:** PAN-1787 (#1815) introduced `resolveHarness()`; this issue fixes the entry
points that still defeat it.

## Glossary

| Term | Meaning |
| --- | --- |
| **Harness** | The coding-agent CLI a spawn runs under: `claude-code`, `pi`, or `codex` (`RuntimeName` in `src/lib/runtimes/types.ts`). |
| **Resolver** | `resolveHarness(input)` in `src/lib/harness-resolve.ts:62`. Precedence: `input.explicit` → `config.roles[role].harness` → `config.providerHarnesses[provider]` → built-in provider default (`getBuiltInDefaultHarness`, openai→codex, kimi/google/zai→pi) → `claude-code`. Winner always passes `canUseHarnessSync()` (ToS gate) and a binary-availability check; failures collapse to `claude-code` with a logged warning. |
| **Explicit harness** | The `explicit` field of `ResolveHarnessInput`. ANY defined value wins the whole precedence chain. Therefore an entry point must pass `undefined` — never a coalesced `'claude-code'` — when the user made no choice. |
| **Explicit-by-default bug** | An entry point that coalesces a missing user choice into `'claude-code'` *before* the resolver runs, turning "no choice" into "explicit claude-code" and silently disabling tiers 2–4. |
| **Provider-default notice** | `logBuiltInDefaultNotice()` (`harness-resolve.ts:56`) — the one-per-provider `console.info` that proves tier 4 fired. Its absence in the PAN-1797 dogfood spawn log was the original evidence. |
| **ToS gate** | `canUseHarnessSync()` (`src/lib/harness-policy.ts`). Blocks Pi + Anthropic + subscription auth. Never weaken or bypass (see `.pan/context/codebase/concerns.md`). |

## Root cause (verified against source 2026-06-13)

`src/cli/commands/start.ts:709`:

```ts
const requestedHarness: 'claude-code' | 'pi' | 'codex' = options.harness ?? 'claude-code';
```

…and `start.ts:1123` passes that always-defined value to `spawnAgent({ harness: requestedHarness, … })`.
`spawnAgent` (`src/lib/agents.ts:3469`) then calls `resolveHarness({ explicit: options.harness, … })`
with `explicit: 'claude-code'` — the resolver IS reached, but explicit wins, no notice is
logged (explicit suppresses `logBuiltInDefaultNotice`), and claude-code+openai+subscription
passes the ToS gate, so the spawn proceeds silently on the wrong harness. This exactly
reproduces the dogfood evidence (gpt-5.5 work agent on claude-code, zero resolver output).

This validation block predates the resolver (PAN-636) and was not in PAN-1787's WI-2
migration table, which listed `spawnRun`/`spawnAgent`/`restartAgent`/plan kickoff/dashboard
route but not the CLI command body. The issue's original "commander default" theory is wrong
(the `--harness` option declares no default; help text is correct); the coalesce lives in the
command function.

## Requirements

- **FR-1** A flagless `pan start <id>` passes `harness: undefined` to `spawnAgent`, so
  `resolveHarness()` owns the decision and a flagless start whose resolved model is
  openai-provider (e.g. gpt-5.5) spawns with `state.harness === 'codex'` and emits the
  provider-default notice.
- **FR-2** `pan start --harness <value>` behavior is preserved: invalid value exits 1 with
  `Invalid --harness value:` on stderr; a disallowed {harness, model, authMode} combination
  (when `--model` is also given) exits 1 with the `canUseHarnessSync` reason; a valid value
  is forwarded as the explicit harness.
- **FR-3** A flagless `pan start` does not run the upfront `canUseHarnessSync` pre-gate at
  all (policy is enforced inside `resolveHarness()` after model resolution).
- **FR-4** `pan strike --dry-run` prints the harness the resolver would actually choose
  (including provider defaults), not a hardcoded claude-code fallback.
- **FR-5** `POST /api/conversations` with a `model` and no valid explicit `harness` resolves
  the initial harness via `resolveHarness({ model })` (no role tier); with no `model` it
  still returns `claude-code`; with an explicit harness it keeps today's
  `canUseHarnessSync`-gated behavior.
- **FR-6** Conversation fork/handoff/respawn harness behavior is byte-for-byte unchanged
  (PAN-1828 owns those semantics).
- **NFR-1** No `execSync`/sync child_process additions on server-reachable paths.
- **NFR-2** All existing tests stay green; `resetHarnessResolveCachesForTests()` is used in
  any new test touching the resolver (its notice set and binary cache are module-global).

   ```ts
   /** Initial harness for a brand-new conversation (no source conversation to
    *  inherit from). Explicit harness keeps the gated behavior; otherwise the
    *  PAN-1787 resolver picks the provider default for the model. No role tier —
    *  conversations are not pipeline roles. PAN-1826. */
   export async function resolveInitialConversationHarness(
     requested: unknown,
     model?: string | null,
   ): Promise<RuntimeName> {
     if (!model) return 'claude-code';
     const explicit: RuntimeName | undefined =
       requested === 'pi' || requested === 'claude-code' || requested === 'codex' ? requested : undefined;
     if (explicit) {
       const decision = canUseHarnessSync(explicit, model, await getProviderAuthMode(model));
       return decision.allowed ? explicit : 'claude-code';
     }
     try {
       return await resolveHarness({ model });
     } catch {
       return 'claude-code'; // HarnessResolutionError (model/auth disallowed) — same posture as today
     }
   }
   ```

## Decisions made in this doc

- **D1 — test seam:** regression coverage via `__testInternals.resolveExplicitHarnessFlag`
  unit tests, not a full `issueCommand`→`spawnAgent` pipeline test. The full path depends on
  real `~/.panopticon` config, projects.yaml, filesystem workspace probing, and a
  `pan workspace create` subprocess — environment-dependent and brittle; no such full-flow
  test exists today. The wiring line (`harness: requestedHarness`) is a one-line diff backed
  by the existing spawnAgent-level test (`agents-spawn-supervisor.test.ts:301`).
- **D2 — conversation scope:** provider defaults apply only to brand-new conversation
  creation. Fork/handoff/respawn = PAN-1828 (inheritance semantics; naive provider defaults
  would 400-reject working plain-fork flows).
- **D3 — resume/restart pinning kept:** `agentState.harness` as explicit is PAN-1787 WI-2's
  documented choice; required for session continuity (a claude-code JSONL cannot resume
  under codex).
- **D4 — dead specialist path not deleted here:** surgical-change rule; recorded in the
  audit table and codebase map instead.
- **D5 — no skill/doc updates needed:** no `--help` text changes (WI-2 of PAN-1787 already
  fixed them), so `scripts/lint-skills.sh` is unaffected.
