# PAN-1801 — CI failure feedback relay: webhook check failures → live work agent

**Issue:** https://github.com/eltmon/panopticon-cli/issues/1801
**Planning mode:** `pan plan --auto` (non-interactive; decisions recorded in `plan.autoDecisions[]`)
**Drafted:** 2026-06-13

## Glossary

- **Check rollup** — GitHub's aggregate of all check runs / commit statuses on a SHA. Surfaced via webhooks (`check_suite`, `check_run`, `status` events) and via `gh pr view --json statusCheckRollup`.
- **Failing-check blocker** — a `BlockerReason` of type `failing_checks` stored on an issue's `ReviewStatus` (`src/lib/review-status.ts:73-77` region). Written by webhook handlers; gates `readyForMerge` (PAN-1650 derivation). Today this is where CI failure information *stops*.
- **Feedback file** — a markdown file at `<workspace>/.pan/feedback/NNN-<specialist>-<outcome>.md`, written by `writeFeedbackFile()` in `src/lib/cloister/feedback-writer.ts:102` (Effect wrapper exported lower in the file). Mirrored into the issue's continue file (`appendFeedbackEntryForIssue`). This is the established "tell the work agent something is wrong" artifact — review convoy, test role, verification gate, and the deacon's merge-time CI path all use it.
- **Agent nudge** — a short tmux/PTY message ("MUST READ: <path>") delivered to the agent session so it opens the feedback file. Canonical primitive: `deliverAgentMessage(agentId, message, caller)` in `src/lib/agents.ts:1445` (supervisor → channels → tmux ladder).
- **Live work agent** — a work agent whose tmux session `agent-<issue-lowercase>` exists on the `panopticon` socket (`sessionExistsSync()`, `src/lib/tmux.ts:494`). Remote (Fly.io) agents have **no** local tmux session and are out of scope here.
- **Settle delay** — a short timer between the first failing webhook event for a SHA and the relay firing, so sibling workflows finish and the relay reports the complete failure set. Pattern precedent: `scheduleMergeStateReconciliation` (`src/lib/webhook-handlers.ts:187`, 30s unref'd `setTimeout`).
- **Inherited failure** — a failing check on the PR whose check name is *also* failing on the PR's base branch HEAD (i.e. main itself is red). Sending the agent to "fix" these wastes a session — they must be labeled, and if *all* failures are inherited the relay is suppressed.

## Problem

Observed on PAN-1579 (PR #1677), 2026-06-12: all four review specialists passed, GitHub Actions CI failed — and nothing told the work agent. The PR sat merge-blocked until a human noticed.

Verified current wiring (2026-06-13):

- `handleCheckSuitePromise` (`src/lib/webhook-handlers.ts:254`), `handleCheckRunPromise` (`:286`), and `handleStatusPromise` (`:514`) ingest CI results and add/remove per-source `failing_checks` blocker entries via `addFailingSource`/`removeFailingSource` (`:137`/`:150`). That blocker only gates merge.
- The **only** CI→agent feedback path is the deacon's `checkFailedMergeRetry` (`src/lib/cloister/deacon.ts:3364`): it fires only when `mergeStatus === 'failed'` **and** review+test are both `'passed'` — i.e. at merge time, after up to five 2-minute retry cycles. CI that goes red while the agent is alive during the work/review window reaches no one.
- Feedback-to-agent plumbing exists and is mature: `writeFeedbackFile` (feedback-writer.ts:102) + agent nudge (deacon precedent at deacon.ts:3394-3412 uses `sendKeys`; the canonical primitive is `deliverAgentMessage`, agents.ts:1445).

## Proposal

A new module `src/lib/cloister/ci-failure-relay.ts` exporting `scheduleCiFailureRelay({ issueId, repo, prNumber, headSha })`, invoked fire-and-forget from the failing branches of `handleCheckSuitePromise` and `handleStatusPromise`. Behavior:

1. **Debounce** per `(issueId, headSha)` — an in-memory `Map` marked at schedule time, bounded (evict oldest past 1000 entries). Re-runs of the same SHA that fail again do not re-relay.
2. **Settle delay**: 60s unref'd `setTimeout`, then relay.
3. **Live-agent gate**: `sessionExistsSync('agent-<issue-lowercase>')`. No session → log and stop (no feedback file either — the deacon's stale-feedback janitor would clear it, and the merge-time path remains the fallback).
4. **Head-move abort**: `gh pr view <n> --repo <repo> --json statusCheckRollup,baseRefName,headRefOid`; if `headRefOid !== headSha`, abort — the new SHA's own events will re-trigger.
5. **Partition failures**: failing entries from `statusCheckRollup` (conclusions in `FAILING_CHECK_CONCLUSIONS`, webhook-handlers.ts:174) vs the base branch's failing check names (`gh api repos/<repo>/commits/<baseRefName>/check-runs?per_page=100`). Same name failing on base ⇒ *inherited*. All inherited ⇒ suppress relay (log only). Base fetch error ⇒ fail open: relay everything with a "could not compare against base" note.
6. **Log excerpts**: `gh run list --commit <headSha> --repo <repo> --json databaseId,name,workflowName,conclusion` → for up to 3 failed runs, `gh run view <id> --repo <repo> --log-failed`, truncated to the last 80 lines per run and ≤8 KB total. No Actions runs found ⇒ feedback carries check names + conclusions only.
7. **Write + nudge**: `writeFeedbackFile({ issueId, specialist: 'ci-monitor', outcome: 'ci-failure', ... })`, then `deliverAgentMessage('agent-<issue>', 'CI is failing on your PR…\n\nMUST READ: <path>\n\nFix the failures, commit, and push — Panopticon detects new commits and re-runs the pipeline.', 'ci-failure-relay')`.

All gh invocations via promisified `execFile` with timeouts (same as `refreshMergeStateFromGitHub`, webhook-handlers.ts:199-214). No `execSync` anywhere — this code is reachable from the dashboard event loop.

## Requirements

### Functional

- **FR-1** — When a `check_suite` webhook arrives with a terminal conclusion other than `success`, or a `status` webhook arrives with state `failure`/`error`, for a tracked-repo PR mapped to an issue, the handler schedules a CI-failure relay for that issue. Individual `check_run` events do NOT schedule a relay.
- **FR-2** — The relay fires at most once per `(issueId, headSha)` pair, marked at schedule time. The debounce map is bounded (≤1000 entries, oldest evicted).
- **FR-3** — The relay delivers only when the work agent tmux session `agent-<issue-lowercase>` exists. No session ⇒ the relay logs and writes nothing. Stopped agents are never auto-resumed by this path.
- **FR-4** — The relay aborts without side effects when the PR head SHA at fire time differs from the scheduled `headSha`.
- **FR-5** — The relay writes a feedback file via `writeFeedbackFile` with `specialist: 'ci-monitor'`, `outcome: 'ci-failure'`, producing `<workspace>/.pan/feedback/NNN-ci-monitor-ci-failure.md`, and nudges the agent via `deliverAgentMessage` with the absolute feedback path in a "MUST READ" message.
- **FR-6** — The feedback body lists each failing check (name + conclusion) and includes failing-log excerpts from `gh run view --log-failed` for up to 3 failed Actions runs on the head SHA, truncated per FR-8.
- **FR-7** — Failing PR checks whose names also fail on the base branch HEAD are listed under an "Inherited from <base> — do not chase these" section. When ALL failures are inherited, the relay is suppressed entirely (log only, no file, no nudge). When the base comparison fetch fails, the relay proceeds with all failures listed as own plus an explicit "could not compare against base" note.
- **FR-8** — Log excerpts are truncated to the last 80 lines per run and 8 KB total across runs; truncation is annotated in the body.
- **FR-9** — Scheduling is fire-and-forget from webhook handlers: the webhook HTTP response is never blocked on relay work, and relay errors are caught and logged, never thrown into webhook dispatch.

### Non-functional

- **NFR-1** — No `execSync`; all subprocess calls are async `execFile` with explicit timeouts (≤15s each, matching `refreshMergeStateFromGitHub`).
- **NFR-2** — Settle timer is `unref()`'d so it never keeps the server process alive.
- **NFR-3** — All tests exercising the settle delay/debounce use `vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync()` — never real timers (repo rule: fake timers for delay-based tests).
- **NFR-4** — The `'ci-monitor'` specialist value is added to both specialist unions (`feedback-writer.ts:19`, `continue-state.ts:93`) so typecheck stays green.

## Planning Q&A

Auto mode (`pan plan --auto`) — no interactive questions asked. All judgment calls are recorded in `plan.autoDecisions[]` in the vBRIEF; the substantive ones:

1. Trigger on `check_suite` + `status` events only, not `check_run` (each Actions workflow has its own suite; run-level events fire before completion and would duplicate).
2. 60s settle delay before relaying, mirroring the `scheduleMergeStateReconciliation` timer pattern.
3. Relay gated on a live local tmux session; no auto-resume, no feedback write when absent. Remote (Fly) agents out of scope.
4. New `'ci-monitor'` specialist value instead of reusing `'merge-agent'`.
5. All-inherited failures suppress the relay; base-comparison fetch errors fail open with a note.
6. No config flag — debounce + live-agent gate + inherited suppression bound the blast radius.
7. gh CLI via async execFile (consistent with `refreshMergeStateFromGitHub`), not the GitHub App token API.
