# PAN-1797 — One-time harness re-default migration on resume of pre-1787 agents

**Issue:** https://github.com/eltmon/panopticon-cli/issues/1797
**Depends on:** PAN-1787 (merged as commit `3da6c9bc1`, PR #1815)
**Planning mode:** `pan plan --auto` (no interactive Q&A; defaults recorded in autoDecisions)
**Verified against codebase:** 2026-06-13 (all file:line references checked at commit `3da6c9bc1`)

## Glossary

- **Session-origin metadata** — the `sessionModel` / `sessionHarness` fields on the agent
  runtime snapshot (`AgentRuntimeState`, `src/lib/agents.ts:2143-2144`). Written via
  `saveAgentRuntimeState()` as a `model_set` event; reduced with `?? prev` semantics in
  `packages/contracts/src/event-reducers.ts:1088-1096`. Introduced by PAN-1787; records which
  model+harness a live session was *started* with.
- **Legacy agent (pre-1787)** — an agent whose runtime snapshot lacks `sessionModel` or
  `sessionHarness` (the exact predicate `sessionResumeDriftReasons()` bails on at
  `src/lib/agents.ts:2164`). Its session predates origin tracking.
- **Drift** — PAN-1787 mechanism: on resume, if origin metadata exists and differs from the
  requested model/harness, `resumeAgent()` drops `--resume` and launches a fresh session
  (`src/lib/agents.ts:4668-4682`).
- **Migration (this issue)** — one-time re-resolution of the harness for legacy agents at
  resume time, replacing stale stored pairings with the PAN-1787 resolver's answer.
- **Caller-explicit harness** — `opts.harness` passed to `resumeAgent()`. Only the dashboard
  resume route passes it, and only when the user picked one
  (`src/dashboard/server/routes/agents.ts:2025-2028`). The deacon
  (`src/lib/cloister/deacon.ts:6434`), CLI (`src/cli/commands/resume.ts:58`), and stuck
  remediation (`src/lib/cloister/stuck-remediation.ts:126`) never pass it.
- **Standard re-onboarding prompt** — `buildDefaultResumeContinueMessage(issueId)`
  (`src/lib/agents.ts:4690`), the "Read .pan/continue.json" kickoff used by the PAN-1787
  drift path (`src/lib/agents.ts:4693-4694`).

## Problem

`resumeAgent()` passes the stored `agentState.harness` to `resolveHarness()` as **explicit**
(`src/lib/agents.ts:4655-4659`):

```ts
const effectiveHarness = await resolveHarness({
  explicit: opts?.harness ?? agentState.harness,
  role: agentState.role,
  model,
});
```

Explicit wins over role/provider/built-in defaults (`src/lib/harness-resolve.ts:69`), so a
pre-1787 agent spawned with the old default (`claude-code` for everything) keeps that pairing
forever — e.g. `gpt-5.5` + `claude-code` instead of the built-in `codex` default
(`src/lib/providers.ts:88`). And because legacy agents have no origin metadata,
`sessionResumeDriftReasons()` returns `[]` (`src/lib/agents.ts:2164`) and `--resume` is kept.
A system restart therefore respawns the whole pre-1787 fleet with exactly the bad pairings
PAN-1787's defaults exist to fix.

**Second gap found during planning:** `resumeAgent()` never writes session-origin metadata
after launching a fresh session — the only writers are `spawnRun`
(`src/lib/agents.ts:3336-3341`) and `spawnAgent` (`src/lib/agents.ts:3687-3690`). Because the
reducer keeps prior values (`sessionModel ?? prev.sessionModel`), a PAN-1787 drift respawn
leaves the *old* origin in place, so **every subsequent resume re-detects drift and burns
another fresh session**. The issue's "one-time by construction: the fresh session writes
origin metadata" is currently false for resumeAgent-launched fresh sessions. This plan fixes
that as FR-5.

## Requirements

- **FR-1** — When `resumeAgent()` runs with no caller-explicit harness (`opts?.harness ===
  undefined`) for an agent whose runtime snapshot lacks `sessionModel` or `sessionHarness`,
  it re-resolves the harness via `resolveHarness({ role: agentState.role, model })` — **no
  `explicit` key**.
- **FR-2** — If the re-resolved harness differs from the stored harness
  (`agentState.harness ?? 'claude-code'`): adopt it (persist to state.json), drop `--resume`
  (fresh session, same plumbing as PAN-1787 drift), deliver the standard re-onboarding
  prompt, and log exactly one migration line per agent naming old→new harness and the model.
- **FR-3** — If equal: keep `--resume`. PAN-1787's backward-compat AC (test
  `tests/integration/agent-spawning.test.ts:621`) remains true for this case.
- **FR-4** — A caller-explicit `opts.harness` bypasses the migration entirely; existing
  explicit semantics are unchanged.
- **FR-5** — Every fresh session launched by `resumeAgent()` (drift, compact recovery, or
  migration) persists `sessionModel`/`sessionHarness` for the new session via
  `saveAgentRuntimeState()`, making drift and migration one-time by construction.
- **NFR-1** — No behavior change for agents *with* origin metadata: PAN-1787's drift rules
  and the `explicit: opts?.harness ?? agentState.harness` resolution stay as-is for them.
- **NFR-2** — New tests are deterministic w.r.t. harness binary availability: stub `pi`/
  `codex` binaries on PATH (pattern at `tests/integration/agent-spawning.test.ts:917-923`)
  and reset the availability cache via `resetHarnessResolveCachesForTests()`.

## Proposal

All changes live in `resumeAgent()` (`src/lib/agents.ts:4517`) plus tests. The migration is
folded into the existing drift machinery so every downstream branch (fresh session id,
`session.id` unlink, message selection, kickoff-style delivery, fresh-respawn logging)
behaves identically to a PAN-1787 drift.

### Before (`src/lib/agents.ts:4655-4660`)

```ts
const effectiveHarness = await resolveHarness({
  explicit: opts?.harness ?? agentState.harness,
  role: agentState.role,
  model,
});
agentState.harness = effectiveHarness;
```

### After (shape — work agent matches surrounding style)

```ts
// PAN-1797: legacy sessions (no origin metadata) predate PAN-1787's session
// tracking and may carry stale model/harness pairings from the old defaults.
// When the caller didn't pin a harness, re-resolve from scratch (no explicit)
// and migrate to the resolver's answer; a changed pairing forces a fresh
// session below, exactly like origin drift.
const storedHarness: RuntimeName = agentState.harness ?? 'claude-code';
const isLegacySessionOrigin = !runtimeState?.sessionModel || !runtimeState?.sessionHarness;
const migrateLegacyHarness = opts?.harness === undefined && isLegacySessionOrigin;
const effectiveHarness = await resolveHarness({
  ...(migrateLegacyHarness ? {} : { explicit: opts?.harness ?? agentState.harness }),
  role: agentState.role,
  model,
});
const legacyMigrationReason = migrateLegacyHarness && effectiveHarness !== storedHarness
  ? `legacy harness migration ${storedHarness}→${effectiveHarness}`
  : undefined;
agentState.harness = effectiveHarness;
```

Then, after the existing `sessionResumeDriftReasons` call (`src/lib/agents.ts:4668`):

```ts
const resumeDriftReasons = sessionResumeDriftReasons(runtimeState, model, effectiveHarness);
if (legacyMigrationReason) {
  resumeDriftReasons.push(legacyMigrationReason);
  console.log(`[agents] ${normalizedId}: PAN-1797 ${legacyMigrationReason} for model ${model} — starting fresh session`);
  logAgentLifecycleSync(normalizedId, `resumeAgent: PAN-1797 ${legacyMigrationReason} for model ${model} — starting fresh session`);
}
```

(For legacy agents the drift array is always `[]` per `src/lib/agents.ts:2164`, so the pushed
reason is the only entry; all PAN-1787 fresh-session plumbing downstream fires unchanged.)

### Origin write on fresh respawn (FR-5) — extend `src/lib/agents.ts:4807-4810`

```ts
await saveAgentRuntimeState(normalizedId, {
  state: 'active',
  lastActivity: resumedAt,
  ...(shouldResumeSavedSession ? {} : {
    sessionModel: model,
    sessionHarness: effectiveHarness,
  }),
});
```

### Behavior notes (decided here, not left to the work agent)

- Comparison baseline is `agentState.harness ?? 'claude-code'`: states with no harness field
  predate PAN-636 and actually ran the old launcher default (`claude-code`).
- The non-explicit resolver path *falls back* to `claude-code` on policy denial or missing
  binary instead of throwing (`src/lib/harness-resolve.ts:85-104`). For a legacy agent whose
  stored harness is policy-denied, today's explicit call throws and the resume fails; after
  this change the migration path falls back gracefully. Strictly better; no action needed.
- If the target binary (`pi`/`codex`) is not installed, resolution falls back to
  `claude-code`, which usually equals the stored harness → no migration, `--resume` kept.
  Correct by design: never migrate onto an uninstalled harness.
- When migration adopts `codex`, the existing `agentState.codexMode = 'work-tui'` line
  (`src/lib/agents.ts:4661-4662`) already applies — codex work agents stay TUI, never exec.
- One-time property: the fresh session writes origin metadata (FR-5), after which PAN-1787's
  normal rules govern. Even before the origin write lands, the migration converges because
  `state.harness` is updated — the next re-resolution is equal → `--resume` kept.
- Fleet wave on first restart is operator-confirmed and bounded: the deacon's concurrency
  and load gates already stagger resumes (`src/lib/cloister/deacon.ts:6413-6428`).

## Intersecting repo rules (restated for the work agent)

- Any retry/delay-based test must use fake timers (`vi.useFakeTimers()` +
  `advanceTimersByTimeAsync`) — never real `setTimeout` waits. The resume tests keep
  `PANOPTICON_PROMPT_READY_TIMEOUT_SECONDS=1` from the suite's `beforeEach`.
- No `execSync` in server-reachable code; no new sync tmux calls. (This plan adds neither.)
- Quality gates before `pan done`: `npm run typecheck`, `npm run lint`, `npm test`.
- Never `git stash`; commit per bead.

## Non-Goals

- No change to `restartAgent` (`newHarness ?? agentState.harness` stays explicit — restarts
  are operator-initiated and can pass `--harness`).
- No change to `spawnRun`/`spawnAgent` origin writes (already correct).
- No bulk offline rewrite of `state.json` files — migration is lazy, at resume time.
- No attempt to distinguish "explicitly chosen" from "old default" legacy harnesses
  (accepted tradeoff per issue; re-pin via Settings/role overrides after migration).
- No config flag / kill-switch for the migration (one-time by construction).
- No dashboard UI changes.
- No change to drift behavior for agents with origin metadata.
